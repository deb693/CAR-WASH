# Database and persistence

MySQL 8/InnoDB with utf8mb4; PHP connects with PDO prepared statements. Appointment storage is UTC with the booking's business timezone recorded. Prices use integer minor units. The complete empty fresh-host installer is [database/install.sql](../database/install.sql), generated by `php scripts/export-schema.php`. Original `schema.sql` plus migrations support existing local installs via `scripts/migrate.php`.

## Entity groups

| Group | Tables / responsibility |
| --- | --- |
| Catalogue | services, vehicle_classes, vehicle_makes, vehicle_models, packages, add_ons, package_add_ons, package_price_overrides, add_on_price_overrides |
| Location/schedule | service_areas, availability_rules, blocked_dates, scheduling_locks |
| Quotes/requests | quotes, bookings, enquiries, idempotency |
| Admin/security | admins, audit_logs, rate_limits |
| Operations | request_history, admin_notes, notifications; worker heartbeat in settings |
| Publication/settings | settings, site_content, faqs, reviews, media |

The installer is authoritative for exact identifiers/columns; `app/Migrations.php` adds legacy-install columns idempotently. Settings and content initialization are one-time and never reset operator edits. Demo seeding has its own marker and is disabled on live non-demo deployments.

Catalogue/configurable entities have validation, optimistic versions and archival where applicable. Archival removes an item from new bookings but keeps records used by older requests. Parent inactivity is respected. A package service/class/tier uniqueness constraint supports restoring an archived tier rather than duplicating it. Overrides and package eligibility use relational keys. Postcodes and working windows are administered through the same API, with overlap validation for hours.

## Transaction boundaries

- Quotes store an immutable server-calculated snapshot and relevant input fingerprint. Submission rechecks current inputs; a changed price/tax/eligibility/coverage or expiry needs a new quote. Unrelated edits do not silently rewrite old bookings.
- Booking submission locks business-day mutex rows, re-evaluates overlapping **whole intervals** including buffer and commits reservation, idempotency result, history and outbox together. Transactions use READ COMMITTED so a waiting allocator sees the preceding commit.
- Rescheduling locks old/new business days in a consistent order. The original interval is kept on proposal, then replaced atomically on accepted agreement. A conflict rolls the operation back.
- Enquiry conversion locks the enquiry, allocates a fresh quote/time and writes a unique source-enquiry booking link. Repeated conversion conflicts and cannot create a second booking.
- Request updates compare a current version, record status/action history and queue necessary notifications in the transaction. Email is sent only after commit by a worker.

## Private data and delivery

Admin passwords use PHP password hashing. SMTP passwords use authenticated AES-256-GCM encryption keyed from APP_KEY. Private sessions, captured `.eml`, logs and backups live in `storage/` above the web root. Capture directories are isolated by database context, so a test database's retention/erasure cannot remove another database's mail.

Notification workers claim rows with SKIP LOCKED and a lease, retry with backoff and retain visible failure states. Rate-limit/idempotency/expired quote cleanup and configurable terminal-customer retention run through `scripts/maintenance.php`. Owner erasure removes customer contact/address, notes and notification payloads/captured mail while preserving nonpersonal commercial snapshots and status history. Database backups still contain data from the backup date and require their own retention policy.

## Backup/recovery

`scripts/backup.php` uses a consistent repeatable-read snapshot, preserving table definitions and data in gzip JSON-lines. Restore validates the format/schema identifiers and refuses any nonempty target database. It requires `--confirm-database` to match private configuration. Local verification restores into a dedicated database and compares all table counts. Back up uploads/configuration and APP_KEY separately; the database snapshot does not contain image files. See [deployment](DEPLOYMENT.md).
